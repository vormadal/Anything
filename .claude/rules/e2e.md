- use Page Object Model for Playwright tests (see `anything-frontend/e2e/pages/`).
- use a global setup file (`anything-frontend/e2e/global.setup.ts`) for common test setup like authentication.
- values that are passed as environment variables to the tests (e.g. API base URL) should be defined in the Playwright config (`anything-frontend/playwright.config.ts`) and accessed via `process.env` in the tests.
- ensure that all tests are independent and can be run in any order (no shared state between tests).
- ensure that tests clean up after themselves (e.g. delete any test data they create) to avoid polluting the test environment and causing flaky tests.

## CI vs Deploy robustness

The CI workflow uses a fresh local database; the deploy workflow runs against the live deployed environment with persistent data and real network latency. Write tests to survive both:

- **Use `page.goto()` for setup navigation.** When a test navigates to a page only as setup (e.g. going to `/recipes/new` to create a recipe), use `page.goto()` directly instead of clicking a UI navigation element. Clicking header icon-links is unreliable in the deployed environment because in-flight API data-loading can cause React re-renders that momentarily detach the element. Reserve UI navigation clicks for tests that specifically assert the navigation element works.
- **Use `page.waitForURL(pattern)` when navigation IS what's being tested.** After a user action that triggers navigation (button click, form submit), prefer `page.waitForURL("**/path")` over `expect(page).toHaveURL(...)` — `waitForURL` is purpose-built for navigation and avoids races where the assertion runs before the router has committed the new URL.
- **Always use timestamp-based unique names for test data** (e.g. `` `E2E Item ${Date.now()}` ``) to avoid collisions with data accumulated from previous runs in the persistent deploy database.
- **Clean up test data after each test** — delete records created during a test (via the UI or a direct API call in `page.evaluate`) so they don't accumulate in the deploy environment and slow down data-fetching for later tests. Wrap creation in `try {} finally { /* delete */ }` (e.g. `shopping-lists.spec.ts` deletes its list via `apiRequest(page, "DELETE", \`/api/checklists/${listId}\`)`).
- **Read `env.apiUrl` for direct API calls in `page.evaluate`**, not a hard-coded `localhost` URL. In deploy the API is proxied at the same origin as the frontend (`E2E_API_URL=E2E_BASE_URL`), so direct fetch calls must use `env.apiUrl` from `e2e/env.ts`.
- **Shared `apiRequest` helper:** `e2e/apiRequest.ts` exports the authenticated `page.evaluate`-based fetch helper (reads the bearer token + household ID from `localStorage`). Import it instead of redefining a local copy per spec file.

## Food-plan suggestion-ranking leakage

`GET /api/food-plan/suggestions` scores every household recipe and returns only the top `count` (max 200, see `GetFoodPlanSuggestions.MaxCount`). A recipe with real planning history scores far higher than a brand-new "not planned yet" recipe (a fixed, low score). An e2e test that creates a recipe (especially one it also schedules) without deleting it leaves a permanently-scoring competitor in the persistent deploy household — over many runs this pushes freshly-created test recipes out of the ranked window and breaks unrelated suggestion tests in `food-plans.spec.ts`.

- Wrap recipe / food-plan-entry / shopping-list creation in `try {} finally { /* delete via apiRequest */ }` even in tests that aren't primarily about food plans (e.g. `flows.spec.ts`, `recipes.spec.ts`).
- **Raising `MaxCount` and adding cleanup is not enough once the shared household is already crowded** — the shared `anything-e2e` household has already accumulated 200+ recipes that permanently outscore a fresh candidate, and code can't undo leaked data. Any test asserting a specific recipe's rank/membership in `/api/food-plan/suggestions` is unreliable against the shared household. Use `food-plans.spec.ts`'s `useEphemeralHousehold` helper: `POST /api/households`, point the page at it via `localStorage.setItem("householdId", ...)`, run the ranking-sensitive assertions there (guaranteed empty → deterministic), then `DELETE /api/households/{id}` in `finally` (which also hides any recipes/entries created in it from every other household — no per-recipe cleanup needed for those tests).

## Offline specs

- **Register the offline transition before acting on it.** After `page.context().setOffline(true)`, wait for the `OfflineBanner` (`await expect(page.getByText(/you're offline/i)).toBeVisible()`) before triggering a shopping-list/checklist mutation. Otherwise the mutation can run before the app registers offline, take the online path, and have to fail a real request before it enqueues — racing the pending-sync-indicator assertion.
- **A full-page reload re-fetches list items, which can lag behind a just-completed write in deploy.** Leaving edit mode via `page.goto(url.split("?")[0])` (there's no client-side "done editing" button — see `src/app/lists/[id]/page.tsx`) wipes the React Query cache and forces a fresh `GET /items`; in deploy that first fetch can miss an item whose `POST` just succeeded (read-after-write lag) and React Query won't refetch on its own. Wrap the post-reload assertions in `await expect(async () => { await page.reload(); /* toBeVisible */ }).toPass()` so a reload re-fetches and self-heals.
- **The "pending indicator clears once back online" assertion needs a reload-retry, not just a longer timeout.** The outbox replay (`useOfflineSync`) is single-shot on the browser `online` event; `replayListQueue` stops a list's queue on the first failed request and only retries on the next sync trigger (`online`/`focus`/`visibilitychange`). A transient first-attempt PUT/POST after reconnect leaves the mutation queued with no further trigger, so a plain `not.toBeVisible({ timeout })` times out even though nothing is broken. Wrap in `await expect(async () => { await page.reload(); /* item visible + no pending */ }).toPass({ timeout: 40000 })` — reloading re-mounts `useOfflineSync` (re-triggers replay) and re-fetches. **Only safe for idempotent replays** (an `update`/check-off PUT); do NOT reload-retry an `add` test — a reload mid-POST re-posts on the next mount and creates a duplicate. The "added while offline" test keeps a plain 20s timeout.
- **The onboarding tour must be pre-suppressed.** The guided tour (`src/hooks/useOnboardingTour.ts`) auto-opens once for any authenticated user with a household when `localStorage.tourSeenVersion` doesn't match `TOUR_VERSION` (`src/lib/tourSteps.ts`), overlaying unrelated tests. Both auth fixtures pre-set the flag — `e2e/global.setup.ts` (chromium project) and `e2e/fixtures/visual-auth.json` (visual project). When bumping `TOUR_VERSION`, update the value in **both** places.

## Visual snapshots (`e2e/visual.spec.ts`)

- **New UI requires a visual snapshot (required, not polish).** Whenever you add a component, page, dialog, or a distinct visual state (empty/error/loaded, a new mode, a new indicator), add at least one Playwright visual snapshot in `e2e/visual.spec.ts` — mock its API data in `setupApiMocks`, drive the UI to the state, and `toHaveScreenshot(...)`. Reviewers rely on these to see UI changes in PRs without running the app; a frontend change that adds UI without a snapshot is incomplete. Use `toHaveScreenshot()`, never Jest `.toMatchSnapshot()`, for visual assertions.
- **Do NOT run `test:e2e:visual:update` in a web session.** Push the spec and let the `update-visual-snapshots` workflow generate and commit the baseline PNGs (see CLAUDE.md → CI Automation & Deployment for the workflow's trigger/`[skip ci]` caveats).
- **You *can* still verify the assertions locally, and it's worth doing** — a bad locator otherwise costs a full CI round trip. The visual project mocks every API call via `page.route`, so it only needs the Next server, not a backend:
  1. `npm run build && PORT=3000 npx next start`. It **must** be port 3000: `e2e/fixtures/visual-auth.json` pins its `localStorage` to origin `http://localhost:3000`, and on any other port `AuthGuard` bounces every test to `/login`.
  2. The pre-installed Chromium in a web session is a different build from the one `@playwright/test` expects (it fails with `Executable doesn't exist at .../chromium_headless_shell-<n>`). Point at the installed one with a throwaway config that spreads `playwright.config.ts` and adds `launchOptions.executablePath: "/opt/pw-browsers/chromium-<n>/chrome-linux/chrome"` to the `visual` project. Playwright resolves `--config` relative to the project root, so write it there (e.g. `playwright.local.config.ts`) rather than in a temp dir.
  3. `E2E_BASE_URL=http://localhost:3000 npx playwright test --config=playwright.local.config.ts --project=visual -g "<area> - "`.
  4. Expect `toHaveScreenshot` failures — baseline diffs for pages you changed, "snapshot doesn't exist" for new ones. Only assertion failures matter. **Delete the throwaway config and any PNG Playwright wrote** before committing: a missing baseline is auto-written on the first run (which is why the same test "passes" if you re-run it), and one generated by the local Chromium build won't match CI's rendering.
- **Reordering fields without changing the page's total height reliably falls under the 2% diff threshold, even for a real layout change.** Swapping two same-shaped fields (a text input for a text input, a label the same length) changes which pixels are where but not how many differ overall, so `--update-snapshots=changed` silently keeps the pre-reorder baseline — this hit `bill-new-recurring`/`bill-new-onetime` twice in the same PR (once reordering a checkbox->Switch + header removal, once reordering the form fields themselves), while a change that adds/removes a visible element (`bill-new-onetime`'s Payment->Date swap, a new tab control) reliably clears 2% on its own. After any pure reorder, verify locally per the steps above and `git rm` the baseline if `--update-snapshots=changed` writes nothing, per CLAUDE.md's stale-baseline gotcha — don't assume a reorder is "small enough" to skip the check.
- **A suggestion/typeahead visual test must target data _not_ already present** in the list it renders over — suggestions filtered against existing items are dropped, so the assertion would silently match an existing row instead of the dropdown.
- **Don't assert `getByRole("alert")` — it collides with Next.js's route announcer.** Next renders a permanent `<div role="alert" aria-live="assertive" id="__next-route-announcer__">`, so `getByRole("alert")` resolves to _two_ elements and fails strict-mode even though the inline form error (`<p role="alert">`) rendered fine. Target the specific message instead, e.g. `page.getByText("Invalid email or password")`.
- **Food-plan weekday-name locators match two rows.** The calendar renders ±1 week, so every weekday appears twice around the fixed clock (2025-01-15). `getByRole("button", { name: /torsdag/i }).first()` silently picks the previous (past) week's day — target the upcoming day via its full aria-label (e.g. `"torsdag, i morgen"`).
